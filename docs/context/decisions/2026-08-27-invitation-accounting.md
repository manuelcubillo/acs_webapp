# ADR: Invitation accounting — half-day slots, counter-based refund capping, settlement markers

**Date**: 2026-08-27
**Status**: accepted
**Modules affected**: actions, auth-tenants, dashboard, history

## Context

The tenant routed to `scan_strategy = 'invitation'` (ADR `2026-07-09-tenant-action-strategies.md`) sells guest access on a half-day basis, held on two number fields of the card: `INVITATIONS` (one covers a whole day) and `HALF_INVITATION` (one covers a single time slot). Two manual actions drive it, `GUEST_ENTRY` and `GUEST_EXIT`; neither is `is_auto_execute`. An entry paid with a full invitation earns the guest a half-credit back if they leave within the same slot; an entry paid with a half-credit earns nothing, and an exit in a later slot earns nothing either, because the guest occupied both. The seam left by the 2026-07-09 ADR provides `handleAction(ctx)` with a card-scoped log reader and field read/write helpers, and nothing else — no clock, no pairing key, no per-visit row. The question was whether those rules could be expressed against that surface without new persistent state. They can.

## Decision

Implement the rules entirely inside `src/lib/action-strategies/invitation-strategy.ts`, with **no schema change and no change to the strategy context**. A time slot is derived from the execution instant in `Europe/Madrid` (`MORNING` before 15:00, `AFTERNOON` from 15:00), never from the raw UTC timestamp. Each entry/exit stamps a discriminated `invitationSettlement` marker (`full_spent | half_spent | half_refunded | none`) into `action_logs.metadata` via the strategy result, and the refund rule counts those markers for today's local date and slot rather than pairing an exit to a specific entry. Actions and fields are matched by UUID only, held in one `INVITATION_CONFIG` block.

## Consequences

- **Positive:**
  - **Slot semantics are timezone-correct by construction.** All day/slot arithmetic goes through one `resolveLocalMoment(instant, timeZone)` using `Intl.DateTimeFormat` with `hourCycle: "h23"`. Madrid is UTC+1/+2 depending on DST, so an entry at 00:30 local belongs to the previous UTC day; computing from the raw instant would bill it against the wrong day. `h23` rather than `hour12: false` because the latter renders midnight as hour "24" in several locales, which would push every midnight execution into `AFTERNOON`.
  - **Counter-based capping needs no pairing key.** There is no visit id linking an exit to its entry, and adding one would mean a new table. Instead `GUEST_EXIT` refunds while `refunded < spent` within the same day + slot. The comparison *is* the cap: at most one half-invitation returned per full invitation consumed, self-enforcing and order-independent, with no state beyond the log.
  - **The metadata marker required no seam change.** `ActionStrategyResult.metadata` was already merged into `action_logs.metadata` by `executeAction`, and `ActionHistoryRecord.metadata` already returned the raw jsonb. The settlement record is therefore unambiguous and survives future edits to the value computation — unlike inferring intent from `before_value` / `after_value`, which cannot distinguish "spent a half credit" from "did nothing" because both leave the target field unchanged.
  - **Matching by id makes the strategy inert until configured.** Field and action names are tenant-editable, so a rename must never change accounting behaviour. A consequence worth having: if the ids are wrong or the tenant's schema is re-provisioned, nothing matches and every execution falls through to the standard path.
  - Decision logic is a set of exported pure functions (`resolveSlot`, `resolveLocalMoment`, `toBalance`, `readSettlement`, `countSettlements`, `decideEntry`, `decideExit`) with I/O at the edges, unit-tested without a database in `src/lib/action-strategies/__tests__/invitation.unit.test.ts`.
- **Negative / trade-offs:**
  - **A repointed target degrades silently-but-loudly rather than failing.** Both actions are expected to target `INVITATIONS`. If a master repoints one, the rules no longer describe reality, and the strategy falls through to standard behaviour and emits a `console.warn`. It deliberately does **not** throw: this is an access-control product, and a misconfiguration must never leave a person stuck at the door. Visibly wrong accounting beats a gate that will not open — the warning is what makes it visible.
  - **Unmarked rows under-refund by design.** Rows written before this strategy shipped carry no marker and are counted as `none`, so an exit will not refund against them. Under-refunding is recoverable by hand; over-refunding hands out credits the tenant never sold.
  - **Inherits the execution path's non-atomicity.** The auxiliary `HALF_INVITATION` write, the target write and the log insert are three separate statements (Neon HTTP has no interactive transactions). Two concurrent executions on the same card also read the same pre-state, so both can spend the same credit. Not worked around; the one-operator-one-card-at-a-gate workflow makes it theoretical.
  - Same-day history is read by paging `getCardActionHistory` (100 rows/page, 5 pages max) and stopping at the first row from an earlier local day — two extra reads per `GUEST_EXIT`.
  - A sub-second skew exists between the strategy's `new Date()` and the DB's `executed_at` default, so an execution landing exactly on 15:00 can be settled as `MORNING` but logged as `AFTERNOON`. Closing it would mean a strategy-supplied `executed_at`, i.e. a change to `executeAction`.
- **Follow-ups:** (none to be built now)
  1. **R3 — insufficient-balance validation.** Wanted: a non-blocking `warning` at scan time when `INVITATIONS <= 0` **and** `HALF_INVITATION <= 0`, plus a real block at `GUEST_ENTRY` riding `allow_override_on_error`, with `GUEST_EXIT` never gated. Deliberately **not** modelled as `scan_validations` rows: that model is single-field and every rule must pass, so `invitations > 0` AND `half > 0` would wrongly deny a card holding only half-credits — the real condition is a sum, not a conjunction. Three findings to preserve: (a) the strategy seam sits one layer *below* where the scan-time notice is assembled — `resolveActionStrategy` is only reached from `executeAction`, while `scanCardAction` and `executeScanWithAutoActionsAction` build their results from `validateScan` and never resolve a strategy at all; (b) `ActionStrategyContext` carries neither `operatorOverride` nor `allowOverrideOnError`, so an in-strategy throw cannot tell a first attempt from a confirmed retry and therefore cannot ride the override machinery; (c) the gate belongs **inside** `executeAction` rather than in each caller, because the external device route (`src/app/api/cards/[code]/actions/[actionDefinitionId]/execute/route.ts`) calls `executeAction` directly and would bypass a caller-level gate. Interim consequence until built: a guest entry at zero balance drives `INVITATIONS` negative.
  2. **The audit trail is incomplete for this tenant.** Both actions target `invitations`, so the two settlements that do not change it (`half_spent`, `half_refunded`) and the one that changes nothing (`none`) log `before_value === after_value`, while the real `HALF_INVITATION` mutation goes through the unlogged `setFieldValue`. `/history`, the CSV export and the activity feed will therefore show entries and exits that appear to have done nothing. Only `metadata.invitationSettlement` records what actually happened, and no surface reads it. A fix belongs in the history layer, not the strategy.
  3. **The replaced stub was live code, not a no-op.** Contrary to ADR `2026-07-09`, the shipped `InvitationActionStrategy` contained a name-matched `accesos` branch with a floating `.then()` whose write raced past the return. Any period during which this tenant ran `scan_strategy = 'invitation'` may contain unlogged writes from it.

## Alternatives considered

- **Pair each exit to its entry via a new `visits` table (or a pairing key on `action_logs`)** — rejected: the explicit constraint was to implement from `action_logs` alone, and a counter comparison over markers already yields the exact cap the domain wants without a migration, a second write path, or an open-visit state machine to reconcile.
- **Infer settlements from `before_value` / `after_value` on the target field** — rejected: it cannot distinguish a half-credit entry from a no-op, since both leave `INVITATIONS` untouched. It also couples log interpretation to the current value computation, so any later change silently rewrites history. The metadata channel was already available and is unambiguous.
- **Match fields and actions by name** — rejected outright: names are tenant-editable from the wizard, so a rename would silently change accounting behaviour on a live tenant. This is what the replaced stub did (`name == "accesos"`).
- **Throw on a repointed target** — rejected: see the trade-off above. A hard failure at a physical gate is worse than degraded accounting.
- **Make the timezone configurable** — rejected as premature. It is one constant, isolated behind `resolveLocalMoment`'s parameter, so making it per-tenant later is a small change rather than a refactor.
